# Data Model: Upstream Coverage Governance

The shapes below are the language-neutral contract between the generator, the checks, and the differential
harness. They are expressed as JSON because the ledger is generated by Node and consumed by both the release
gate and the Dart-side harness; the Dart implementation mirrors them only where it must emit a result.

## State

`coverage/state.json`

```json
{
  "target_upstream_sha": "780bf31fcaeb252fa9b68df3964c735eae75bde3",
  "verified_upstream_sha": "780bf31fcaeb252fa9b68df3964c735eae75bde3",
  "target_advanced_at": "2026-11-22",
  "verified_advanced_at": "2026-11-22",
  "verified_by": "pi#11"
}
```

- `target_upstream_sha` — the commit the port aims to match. Advanced by the daily sync.
- `verified_upstream_sha` — the commit at which every applicable row is `verified`. Advanced only by a
  completed slice.
- `verified_by` — the issue or slice that last advanced the verified SHA (traceability, not a gate input).
- Invariant: `verified_upstream_sha` MUST be an ancestor of (or equal to) `target_upstream_sha`. A verified
  SHA that is not reachable from the target is a state error, not a warning.

### Row status

| Status | Meaning | Gate effect |
| --- | --- | --- |
| `unported` | No Dart implementation exists. | Fails the release gate; must carry a divergence + issue. |
| `in_progress` | A Dart implementation exists but is incomplete. | Fails the release gate; must carry a divergence + issue. |
| `implemented_unverified` | Dart code exists but no passing evidence is bound. | Fails the release gate; must carry a divergence + issue. |
| `verified` | Named evidence exists and passes at the declared SHA. | Passes the release gate. |
| `not_applicable` | Upstream behavior is out of scope for the port. | Passes only with an approved platform/scope reason. |

### Row invariants

- `id` is stable across SHAs: `(<area>, <upstream_path>, <export>, <behavior_kind>)` slugified.
- A row with status other than `verified` or `not_applicable` MUST have non-null `divergence` and `issue`.
- A row with status `not_applicable` MUST have a non-null `divergence.reason` and an approval.
- A row with status `verified` MUST have an `evidence` object naming either a differential scenario or an
  upstream-derived Dart test; the checker re-runs the named evidence.
- `dart_test`, when non-null, MUST resolve to an existing path under `pi_agent/test/`.

## Export Inventory

`coverage/upstream/<sha>/exports.json`

```json
{
  "schema_version": 1,
  "upstream": { "repo": "earendil-works/pi", "sha": "<sha>" },
  "packages": [
    {
      "area": "ai",
      "npm_name": "@earendil-works/pi-ai",
      "exports": [
        {
          "name": "streamCompletion",
          "kind": "function",
          "type_only": false,
          "source": "packages/ai/src/api/completions.ts",
          "schema": null
        }
      ]
    }
  ]
}
```

The export diff compares this file between the previous and current target SHA and reports, per package:
`added`, `removed`, `renamed` (same symbol under a new path). A removed or renamed export without a
corresponding manifest update fails `check-coverage.mjs`.

## App Decisions

`coverage/upstream/<sha>/app-decisions.json`

```json
{
  "schema_version": 1,
  "decisions": [
    { "path": "apps/p2", "decision": "not_applicable", "reason": "…", "approved_by": "arrrrny" },
    { "path": "apps/p3", "decision": "adapt", "reason": "…", "approved_by": "arrrrny" }
  ]
}
```

- `decision` ∈ `port` | `adapt` | `not_applicable`.
- `reason` is required for `adapt` and `not_applicable`.
- `approved_by` is required for `not_applicable`.
- The set of `path` values MUST equal the set of `apps/*` directories at the pinned SHA. Missing or extra
  entries fail the check.

## Differential Scenario

`coverage/differential/scenarios/<name>.json`

```json
{
  "schema_version": 1,
  "name": "tool-arguments-invalid",
  "area": "agent",
  "row_ids": ["agent.agent-loop.tool-arguments-validated"],
  "provider": { "kind": "scripted", "turns": [] },
  "clock": { "kind": "virtual", "start": "2026-01-01T00:00:00Z" },
  "storage": { "kind": "memory" },
  "crash_points": ["after-commit-1"],
  "normalization_version": 1
}
```

- `provider.kind` is `scripted` or `cassette`; a cassette scenario names a sanitized fixture path and MUST
  NOT name a live endpoint.
- `crash_points` are labels the harness acts on for durable rows; the same labels are interpreted by both
  implementations.
- A scenario names the `row_ids` it produces evidence for; a row may have more than one scenario.

## Normalized Outcome

Emitted by both implementations as JSONL; compared after normalization.

```json
{ "seq": 1, "type": "event", "name": "agent_start", "payload": {} }
{ "seq": 2, "type": "transcript", "role": "user", "content": "…" }
{ "seq": 3, "type": "state", "path": "$.turns", "value": {} }
{ "seq": 4, "type": "commit", "id": "c1", "entries": [] }
{ "seq": 5, "type": "error", "code": "argumentsError", "message": "…" }
{ "seq": 6, "type": "usage", "input": 0, "output": 0, "cache": 0 }
```

Normalization rules (versioned by `normalization_version`):

- Timestamps are replaced by their ordinal within the stream.
- Generated IDs are replaced by role-based placeholders (`<commit-1>`, `<tool-call-1>`) assigned in first-
  seen order.
- Events inside one turn that are declared freely interleavable are sorted by `(name, canonical-json)`;
  events across turns keep their order.
- Object keys are emitted in sorted order.
- Absolute paths are reduced to repo-relative paths.

## Report

`coverage/upstream/<sha>/report.md` is a pure function of `manifest.json`: one section per package, a status
table, and a "not verified" section listing every row with its divergence and issue. It is regenerated, never
hand-edited, and its content is not an input to any gate.

## Release Evidence

Produced by `check-release-evidence.mjs`, printed to stdout and (on success) recorded in the release notes.

```json
{
  "schema_version": 1,
  "verified_upstream_sha": "<sha>",
  "target_upstream_sha": "<sha>",
  "resolved": true,
  "rows_total": 0,
  "rows_verified": 0,
  "rows_not_applicable_approved": 0,
  "failures": []
}
```

`resolved` is `true` only when the target equals the verified SHA, every applicable row is `verified`, and
every exclusion is approved. Any `failures` entry is a release blocker.
